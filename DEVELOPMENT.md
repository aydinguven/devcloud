# DEVELOPMENT

## Project snapshot

- DevCloud: self-hosted browser IDE platform (FastAPI + Podman), controller plus outbound-only CPU/GPU workers, MLflow model serving.
- Source: `https://github.com/aydinguven/devcloud` (GitHub by owner's choice; not on Forgejo). Default branch `main`, latest release `v3.22.0` (`v3.18.0` was tagged but its release failed and stays a draft).
- Release process: bump `app/__init__.py` `__version__` via PR, then push tag `vX.Y.Z` on the merged `main` commit. `.github/workflows/release-platform.yml` builds the bundles, creates the GitHub Release and advances the `stable` update channel.
- Deployment: own installer/offline bundle (`INSTALL.md`, `AIRGAP.md`, `WORKERS.md`); not a Tupperware project.
- Local setup: `python -m venv .venv`, `.venv\Scripts\python -m pip install -r requirements.txt`, run `python run.py` (http://127.0.0.1:8000).
- Tests: `.venv\Scripts\python -m pytest -q`. No CI on PRs/merges; run this before every PR. The release workflow's `tests` job gates publishing.

## Decisions

- 2026-10-20 (3.22.0, PR #71, migration 32; spec `.kiro/specs/mlflow-kubernetes-publish/`): the Kubernetes deploy target ends at the deploy registry. AI Factory builds the MLflow model version (or reuses a ready build), then the controller runs `skopeo copy` from the intermediate registry to `{deploy registry}/{rfs_code}/{app_name}:X.Y.Z` and records the digest. The platform team re-tags (`X.Y.Z-RC.BN` test, `X.Y.Z-BN` prod) and deploys with Helm, with secrets coming from Vault → External Secrets → `envFrom`. AI Factory never handles database credentials. Aydin chose:
  - Publishing is open to every AD user and admin for now (`app.kubernetes_publish.can_publish_images`), so it can be limited later.
  - Releases get their own tables (`mlflow_image_releases`, events) instead of extending `mlflow_deployments`; status is a plain string column.
  - The modal drops the namespace, replica and flavor inputs; the namespace comes from an admin-defined Kubernetes project (Admin > Kubernetes, new section 07).
  - After a publish, AI Factory sets `aifactory.image` and `aifactory.image_digest` tags on the MLflow model version. This is the first MLflow write; a failure there is only a warning.
  - No CA file for the deploy registry: an optional "TLS doğrulama" switch maps to `--tls-verify=false` / `--dest-tls-verify=false` (which also allows plain HTTP), and the registry test then also tries `http://`. An optional `v2s2` manifest conversion covers a registry that rejects OCI.
  - Publish-only builds are not imported into `WorkspaceImage`, so workers do not sync them. `_build_image` became `ensure_model_build(owner, import_image=...)`, shared by deployments and releases; AI Factory still requires an imported build, so it rebuilds rather than reusing a publish-only one. The three GC functions count in-progress releases as references.
  - The release loop (`image_release_service`, task "Kubernetes imaj yayın kuyruğu") is separate from the sequential deployment loop.
  - The tag is checked before the build and again before the release enters `publishing`, so `publishing` means "the tag was free and the copy began". Any failure in that state, and recovery after a restart, goes through `_settle_started_publish`. If the tag exists, the release is published, with a warning and the MLflow tags. If it does not, the release fails, or recovery requeues it. If the registry cannot be reached, the release is checked again 30 s later. A pushed tag is never left behind a failed release, which is what lets application delete remove failed releases.
  - Never-overwrite is check-then-copy, and `skopeo copy` replaces tags. Nexus "Disable redeploy" on the hosted repository is the real guarantee and is documented as a prerequisite.
  - A failed release keeps its build for 24 h (`_FAILED_RELEASE_BUILD_RETENTION`), so a retry after fixing Nexus rights or the manifest format does not rebuild. Published releases do not pin their build.
  - Users who cannot publish get no targets from `/api/mlflow/kubernetes/options`. No worker change: the build RPC is unchanged.
  - A behavioural review compared HEAD's `_build_image` with the new `ensure_model_build` in six scenarios; AI Factory behaviour is identical. The one intended difference: a previous build still used by a release is not cleaned up.

- 2026-10-15 (3.21.1, PR #68): native rootless workers had `XDG_RUNTIME_DIR=/run/user/0`. In system units, systemd's `%U` is the service manager's uid (0), not the `User=` account's. So `devcloud-worker.service` created a root-owned `/run/user/0`, and every Podman call failed with `mkdir /run/user/0/libpod: permission denied`; this was seen on IDMSYAPZET7 as image sync never loading. The unit now uses `{{UID}}`/`{{USER}}`, and `InstallerEngine._install_services` renders the service account's numeric uid (`_service_uid`, shared with `_prepare_images`). The install, repair and update plans all rewrite the unit, so updating a worker fixes it. Hosts patched by hand with a `runtime-dir.conf` drop-in get the same values and can keep it. The old string-pinning tests asserted `%U` and were replaced by one test that renders the installed unit. No schema change.
- 2026-10-15 (3.21.1, PR #69): the dashboard's two user cards (usage and remaining quota) are one **Kota Kullanımı** card. Each row shows `kullanılan / toplam · X kaldı` with a usage bar that turns gold at 80% and red at 95%. Display only; `user_usage` is unchanged. No schema change.

- 2026-10-15 (3.21.0): Placement tags for workers and workspaces (migration 31, `app/placement.py`).
  - **Tag catalog.** Admins manage `placement_tags` rows of two kinds. `datacenter` tags (IDM and ODM are seeded) give a worker at most one datacenter. `custom` tags are capabilities a workspace can require (the worker must carry all of them).
  - **Columns.** Workers store `nodes.datacenter` and `nodes.tags_json`. Workspaces store the request they were created with in `workspaces.datacenter` and `workspaces.tags_json`, where `""` means Any.
  - **Choices Aydin made:**
    - GPU/CPU class comes from the detected hardware (`is_gpu_worker`: reported accelerators, or NVIDIA status `ready`/`error`), not from a tag.
    - CPU workspaces are **blocked** from GPU workers. This replaces the old soft `gpu_worker_penalty` for workspaces. `select_worker_node` (MLflow/custom image builds) passes `reserve_gpu_workers=False` and keeps the soft preference.
    - Users pick the datacenter and tags at create time.
    - Tags are defined in the Admin panel.
    - The defaults are CPU and Any. An unassigned worker serves only Any workspaces.
  - **Availability follows the request.** Flavor availability (`GET /api/workspaces/flavors?datacenter=&tags=`) and the GPU picker apply the same constraints, and the dashboard re-checks the GPU cards when the selection changes.
  - **Existing workspaces.** Restarts stay pinned and are not re-checked against tags, so CPU workspaces already on GPU workers keep running.
  - **Legacy labels.** The free-form `labels_json` labels stay but remain informational.

As the agreed compromise, `release-platform.yml` has a `tests` job: the full suite on Python 3.12 with a PostgreSQL 16 service, read-only permissions. It runs in parallel with the builds, so it adds no wall time, and `publish` requires it. A failing suite therefore leaves the release as a draft and keeps `stable` where it was. Images that the build jobs already pushed stay in the registries but are not released. `test_ci_runs_tests_without_write_permissions`, which only pinned `ci.yml`'s wording, was deleted with it (explicit exception to the no-test-changes rule). Still run the local suite before opening a PR.

- 2026-10-14 (3.18.2, PR #59): a TCMB Code workspace must never start silently unconfigured. `WorkspaceAiConfig.tcmb_code_problem` names the Admin-side cause (card not distributing, Workspace AI off/no gateway, no models) in the deploy stream and controller log. TCMB Code workspaces are scheduled only on workers reporting 3.18.0+ (`app.tcmb_code.MIN_AGENT_VERSION`; an unreported version is allowed). `ai_config_digest` stores only the digest a worker actually applied (empty for pre-3.18 workers) and is salted (`CONFIG_DIGEST_SALT`), so every container recorded by 3.18.0/3.18.1 is rebuilt once on its next start. No schema change, so 3.18.1 rollback stays possible.
- 2026-10-15 (3.19.0): new built-in template `vscode-cuda` (**TCMB Code (CUDA)**) for GPU workers: `containers/vscode-cuda` is the vscode-tcmb Containerfile plus CUDA 13.4 from NVIDIA's Debian 13 repo (the `cuda:*-devel` package set without Nsight Compute), cuDNN 9 and NCCL, all version-pinned; the keyring deb is checksum-pinned. The NVIDIA driver is never baked in (the build fails if `libcuda.so.1`/`libnvidia-ml.so.1` is present); host CDI injects it, so hosts need driver 580+. Two new `WorkspaceTemplate` fields: `requires_accelerator` (CPU flavors refused by `flavor_mismatch` in both create routes, CPU flavor cards locked in the dashboard, image omitted from `/api/agent/images/catalog` for workers whose heartbeat has no NVIDIA `ready`/`error` status) and `min_agent_version` (`3.19.0`: an older worker would register the unknown template as a Cline custom template; combined with the TCMB Code minimum in `template_minimum_agent_version`). The image is ~7 GB unpacked, so it is registry-only (no GitHub release archive) and its CI job frees runner disk first. TCMB Code version, checksum and `lancedb/` are duplicated from vscode-tcmb; the smoke test enforces the version. No schema change.
- 2026-10-15 (3.21.0, never released as 3.20.1): on hardened hosts with a 027/077 root umask, a native (GPU) worker install created `/opt/devcloud`, `/var/lib/devcloud/releases` and the release `.venv` unreadable to the service user, so `devcloud-worker.service` failed with `203/EXEC Permission denied` and the installer stopped at `systemctl is-active`. `devcloud-setup.sh` and `app.installer.cli.main` now set umask 022; secrets keep their explicit modes (`_atomic_write`, 0600 backups). `app.installer.verify_worker` used httpx's bundled certifi list, so a controller CA added with `update-ca-trust` passed the agent but failed install verification (`CERTIFICATE_VERIFY_FAILED`); it now builds the same `ssl.create_default_context(cafile=DEVCLOUD_AGENT_CA_FILE)` as the agent. No schema change.
- 2026-10-15 (3.20.0): Rocky/RHEL 9.x hosts are supported by the installer (worker and controller). EL9's `python3` is 3.9, below the 3.11 floor (StrEnum, `slots=True`, `asyncio.timeout`) and incompatible with the cp312 wheels, so `app/installer/platform.py` maps EL9 to `/usr/bin/python3.12` (`host_python`) plus `python3.12`/`python3.12-pip` (`host_python_packages`). `devcloud-setup.sh` installs and execs that interpreter; the engine uses it for the native venv and renders it into `devcloud-update.service` (`{{PYTHON}}`). EL10 behavior is unchanged. Offline packaging accepts a `*-9-x86_64` RPM profile, but CI still builds EL10 bundles only: an EL9 air-gap bundle must be built on an EL9 host. No schema change.
- 2026-10-15 (3.19.1): Admin > Workspace Image'ları. **Devre Dışı Bırak** used to fail silently: the 409 for "in use" landed in the banner at the top of the page. "In use" also meant *any* workspace ever created from the image, which contradicted the documented "existing workspaces unaffected". Disable is now always allowed. `/api/agent/images/catalog` keeps sending a worker every image pinned by one of its workspaces (`Workspace.image_id`), so those workspaces still restart. Enabling or importing a version disables all the template's other versions, except MLflow model images (`source_type == "mlflow_model"`), which are one per model version. **Sil** returns 409 naming the pinned workspaces, matching the FK RESTRICT. MLflow model images used to be undeletable because every image is referenced by its own build. They now return 409 naming the deployments that use them; otherwise they go through `enroll_model_build_cleanup` + `garbage_collect_model_build`. That returns 200 when done, or 202 with the reasons it collected (offline worker, worker `rmi` failure, registry refusal) while the background loop retries. Action results render on the image's own row. No schema change.

- 2026-10-09: Per-component health lives on a public `/status` page fed by `GET /api/health` (`app/health.py`). `/healthz` and `/readyz` are unchanged; `/readyz` stays database-only so an LDAP or LiteLLM outage never restarts the controller. Required components are database, controller storage, workers, background tasks, and LDAP/AD when it is enabled. An optional component (LiteLLM, MLflow, registry, HTTPS, update) can only degrade the overall status. Anonymous callers get statuses, summaries and latency; hosts, paths and raw errors are admin-only. Reports are cached 15 s and built single-flight. Thresholds:
  - worker heartbeat: over 60 s degraded, over 120 s down;
  - disk: 85 % degraded, 95 % down;
  - TLS certificate: under 14 days degraded;
  - failed update: degraded for 7 days.

  Background loops report into `app/task_health.py`. Workers add `capabilities.health` (Podman info, storage write probe; refreshed every 60 s) to the heartbeat; older agents simply omit it.
- 2026-10-09: Unit-head and Genel Müdür titles match with parenthesized qualifiers removed (`app.auth.ldap.fold_title`), so acting heads such as Funda Kaplan (K000419, `MÜDÜR (TEDVİR)`) count as `MÜDÜR`. Before 3.16.1 her teams were shown as reporting straight to the Genel Müdürlük.

A publish failure after an applied update exits 3; `queued_update` records `succeeded` plus a `warning`. `devcloud-setup.sh --yes publish-worker-bundle` republishes the installed release. Updates check free space before staging, and a best-effort `cleanup` step (it must never raise, or the plan rolls back) keeps the current and previous release, their runtime images and the 3 newest pre-update backups.
- 2026-10-08: MLflow deploys offer two targets: **AI Factory** (the existing managed service on DevCloud workers) and **Kubernetes** (planned: serving image -> Nexus -> workflow -> TCMB Kubernetes). Kubernetes is UI only and disabled (`DEPLOY_TARGETS.kubernetes.available = false` in `mlflow_deployments.js`) until the backend exists.
- 2026-10-08: Update progress is a best-effort JSON file next to the queue (`app/installer/progress.py`, stdlib only): the root updater resets it and passes `DEVCLOUD_UPDATE_PROGRESS_FILE`; the installed CLI reports download bytes and verification; the target engine reports each plan step, the controller health wait and rollback (it falls back to `/var/lib/devcloud/update-queue/progress.json` when the variable is missing, so a 3.14 updater still gets step progress). - 2026-10-07: Releases always build and ship controller and worker images; a workspace image is built only when `containers/<image>` changed since the newest *published* `vX.Y.Z` release, or when forced with the `rebuild_workspaces` dispatch input. Migration 25 turns every legacy value that differs from the configured default into an override, so effective quotas do not change on upgrade.

- 2026-10-06: Workspace AI uses the owner's own LiteLLM *workspace key* (separate from the personal key, encrypted, never shown) only when the owner opted in on the GenAI tab and GenAI and Workspace AI point at the same LiteLLM; otherwise the shared key. Keys bind to the first team in the admin priority list the user belongs to; new users join the default team.

## Known issues and risks

- TCMB Code 7.8.3 VSIX stores every `bin/` entry as mode 0664 and code-server keeps the zip modes, which failed the `v3.18.0` build; since 3.18.1 the Containerfile restores 0755 on the non-`.js` files in `bin/`. Re-check this when updating the VSIX. The Linux x64 VSIX is the public GitHub release asset `tcmb-code-7.8.3`, pinned by SHA-256 in `containers/vscode-tcmb/Containerfile`.
- The failed `v3.18.0` run left a draft GitHub Release `v3.18.0`, and its successful Rocky platform job may have pushed 3.18.0 controller/worker images. Nothing points at them; the release scope ignores drafts.
- TCMB Code: the shared indexing key is readable by every TCMB Code user inside their workspace; it must be restricted to the embedding model and budgeted in LiteLLM. Recreating a container on a config change resets state outside `/home/coder/project` (extra extensions, TCMB Code chat history under `~/.local/share/kilo`).
- The `kilo-code.new.model.*` settings and the global `~/.config/kilo/tcmb.jsonc` were verified in a running `vscode-tcmb-3.18.1` container on 2026-10-14 (CI probe): the agent loads the file and the picker shows the configured default model. `KILO_DISABLE_MODELS_FETCH` does not stop the agent fetching Kilo's model list and marketplace from `api.kilo.ai`; offline this should only fail, but check for start-up delays on IDMVAIFACT1.
- In Restricted Mode VS Code disables TCMB Code entirely (the extension declares no `untrustedWorkspaces` support); users must trust `/home/coder/project`.
- The agent rewrites `~/.config/kilo/tcmb.jsonc` on first run (adds `permission.bash: allow`, pretty-prints) and on settings changes in its UI; DevCloud overwrites it on every container start, so UI-made global settings do not survive a restart.
